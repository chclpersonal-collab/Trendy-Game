# v3.5 Performance Hotfix — Shield Targeting and UI Cadence

## Classification

**Performance bug fix / no intended balance change.**

The user reported approximately one rendered frame per second and supplied `musketeer-state-v3.5.0-seed-3101678311-war-1-t-153s.json`.

## Export evidence

At 153.113 simulated seconds the export contained:

- speed: 4×
- viewport: 1280×631
- device pixel ratio: 2
- 83 living musketeers
- 12 living commanders
- 95 living actors total, 97 actor records including two corpses
- six companies per side
- one active shot and zero smoke particles
- only 16 flight-recorder samples

The severe slowdown therefore appeared before army or effect limits were approached. The export does not contain CPU profiles, so the exact runtime cost is inferred by matching this actor count to the active v3.5 code.

## Confirmed code hotspot

The v3.5 shield-aware target selector did all of the following for each targeting request:

1. copied and sorted the full eligible enemy pool;
2. recomputed each comparator score repeatedly during sorting;
3. rescanned the same full pool inside every score to find lower-rank shields;
4. repeated target selection several times for the same actor during one simulation step;
5. updated the entire text information rail every rendered frame.

With roughly 47 enemies per side, one sorted selection could perform tens of thousands of shield checks. At 4× speed, multiple simulation steps and repeated actor target requests could occur inside one rendered frame.

## Hotfix contract

- Build one lower-rank shield index per actor-update step.
- Replace sorting with a single-pass minimum preserving score and actor-ID tie-breaking.
- Cache each actor's `enemy`, `combat`, `siege`, and `breach` target for the current step.
- Recompute immediately when a cached target dies.
- Preserve rear-threat priority, BREACH/SIEGE range filters, commander fallback, shield depth/lane, and lower-rank penalty values.
- Leave direct test/helper calls uncached so controlled position changes remain immediately observable.
- Refresh the text-heavy information rail at 10 Hz while keeping simulation and canvas drawing on `requestAnimationFrame`.
- Export performance telemetry: candidate scores, shield checks, cache hits/misses, step time, frame time, observed FPS, and UI-update count.

## Protected invariants

The hotfix must not intentionally change:

- economy prices, income, maintenance, bounty, or reserves;
- HP, Mana, regeneration, range, or promotion behavior;
- lower-rank shielding geometry or target-score values;
- rear-threat priority;
- company commands, formations, fortress rules, or siege thresholds;
- 150 soldiers per army, 14 per company, or 11 companies per army;
- F/E/D/C unlock state;
- Commander Forms I and II.

## Verification gate

- Existing shielding and formation tests remain green.
- Existing full deployed Playwright suite remains green except independently unresolved balance gates.
- A controlled export-sized scenario creates at least 90 living actors.
- Full-pool sorts remain zero.
- Repeated target requests produce cache hits.
- Last-step candidate evaluations remain bounded below four full actor-matrix passes.
- A 4× crowded-browser probe produces more than 15 animation frames in 1.6 seconds on the GitHub runner.
- UI updates remain bounded by the 100 ms refresh interval.

## Status

**Candidate until deployed performance verification completes.** A fresh real-device export after deployment is still required because the submitted JSON records game state, not browser frame timings or a JavaScript CPU profile.
