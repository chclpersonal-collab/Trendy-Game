# v3.5 Performance Hotfix — Shield Targeting and UI Cadence

## Classification

**Accepted performance bug fix / no intended balance change.**

The user originally reported approximately one rendered frame per second and supplied `musketeer-state-v3.5.0-seed-3101678311-war-1-t-153s.json`.

## Original failure boundary

At 153.113 simulated seconds the original export contained:

- speed: 4×
- viewport: 1280×631 at device-pixel ratio 2
- 83 living musketeers and 12 commanders
- 95 living actors total
- six companies per side
- one active shot and zero smoke particles

The slowdown therefore appeared far below army and effect ceilings.

## Root cause

The original shield-aware target selector:

1. copied and sorted the full eligible enemy pool for every target request;
2. recalculated both target scores during every sort comparison;
3. rescanned the same pool for lower-rank screens inside each score;
4. repeated target selection for the same actor and mode in one simulation step; and
5. rewrote the complete text information rail every rendered frame.

At 4× speed those nested scans were multiplied by several simulation steps per rendered frame.

## Implemented hotfix

- Build one lower-rank shield index per actor-update step.
- Replace full-pool sorting with a single-pass minimum preserving score and actor-ID tie-breaking.
- Cache `enemy`, `combat`, `siege`, and `breach` targets per actor for the current step.
- Recompute immediately when a cached target dies.
- Preserve rear-threat priority, SIEGE/BREACH filters, commander fallback, shield geometry, and penalty values.
- Keep direct helper/test calls uncached so controlled actor movement remains immediately observable.
- Refresh the text information rail at 10 Hz while simulation and canvas drawing remain on `requestAnimationFrame`.
- Export candidate scores, shield checks, cache hits/misses, step time, frame time, FPS, and UI cadence.

## Automated evidence

GitHub Actions run `31869048466` reached 38 of 46 tests before the 15-minute workflow limit cancelled the remaining long simulations.

The focused performance tests passed:

- export-sized 95-actor synchronous scenario: 169.1 ms for two simulated seconds;
- zero full-pool sorts;
- last step 3.0 ms and maximum step 8.2 ms;
- crowded 4× browser probe: 97 frames over 1.603 seconds;
- measured browser probe: 60.86 FPS, 7.4 ms last frame, 17.8 ms maximum frame;
- UI updates remained at the 100 ms cadence.

The cancellation was a verification-budget problem in sequential multi-seed tests, not a performance-test failure.

## Real-device acceptance evidence

The post-hotfix export `musketeer-state-v3.5.0-seed-1597106260-war-1-t-1725s.json` was generated on the same Windows/Chrome environment after a much longer 4× run.

It recorded:

- 1,725.729 simulated seconds;
- a flight-recorder peak of 147 versus 148 musketeers plus 22 commanders, or 317 living actors;
- 24,449 rendered frames and 4,663 text-UI refreshes;
- 94.18 reported recent FPS;
- 1.3 ms last simulation step and 24.7 ms maximum step;
- 1.8 ms last frame and 79.4 ms maximum frame;
- zero full-pool sorts;
- approximately 65.1% target-cache hit rate.

Assuming the run remained at 4× for its full duration, the frame counter corresponds to approximately 56.7 average rendered FPS and the UI counter to approximately 10.8 updates per second. That average is an inference from the export counters; the directly recorded recent FPS is 94.18.

## Decision

**Performance hotfix accepted.**

The original one-frame-per-second blocker is not reproduced in the long real-device sample, including near the army cap. Further targeting optimization is not justified before another export shows a measurable responsiveness regression.

## Remaining verification work

- Repair the CI layout so long economy, ecology, natural-siege, and 2,200-second gates do not exceed the workflow limit.
- Continue to export frame/step telemetry in later large battles.
- Treat isolated maximum-frame spikes separately from sustained low FPS.
